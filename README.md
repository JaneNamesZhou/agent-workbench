# 🚀 个人 AI 工作台 (Personal AI Workbench)

> 一个只为我自己的日常工作服务的 AI 工作台：读我的文档、改我的代码、跑我的运维脚本。
> 同时，它也是我从零学习 Agent 工程化的载体——边学边建，建到哪、学到哪。

---

## 🎯 我想要的工作台最终是什么样

不是「一个能聊天的机器人」，而是**能动手替我干活的工具集**。最终形态按使用场景定义：

| 使用场景 | 工作台要替我做的事 | 依赖的核心能力 | 现状 |
| --- | --- | --- | --- |
| 个人知识问答 | 把我积累的笔记 / WIKI 变成可检索、可引用的问答库 | RAG 全链路、向量库、重排 | 📋 规划中 |
| 代码辅助 | 读懂本地仓库，按需求改代码并自查 | 工具系统、多步规划、校验回路 | 📋 规划中 |
| 自动化运维 | 执行常用命令、按执行结果继续决策 | Shell 工具、权限边界、危险命令拦截 | 📋 规划中 |
| 日常任务代办 | 一句话下达任务，自主拆解并跑完 | Agent Loop、多智能体协作、评测 | 🚧 最小循环已跑通 |
| 全过程可追踪 | 每次调用花了多少 Token、为什么走这一步 | 链路追踪、结构化日志、评测集 | 📋 规划中 |

这张表是项目的北极星：**新功能是否值得做，取决于它是否让上表某一行从「规划中」变成「已落地」**。

## 📍 当前仓库是什么

坦白说：现在整个仓库只有一个 [hello-agent.py](file:///d:/code/agent-workbench/hello-agent.py)——一个**手写的最小 ReAct 闭环**，用模拟的天气工具验证「模型输出 → 解析行动 → 执行工具 → 结果回填 → 继续推理」这条链路是通的。

它是工作台的**地基**，不是工作台本身。距离上面那张表，还差工具系统、记忆、网关、RAG、多智能体、可观测性六大块。

**为什么先手写、不直接上框架**：因为我想亲手撞一遍那些被框架藏起来的问题——工具描述怎么写模型才听得懂、正则解析什么时候开始崩、上下文什么时候爆、循环什么时候停不下来。这些问题只有手写过一遍才会长在自己的判断里；撞完再引入 LangGraph 重构，才谈得上「框架解决了什么、代价是什么」。

## 📓 项目性质：以学习为驱动的建造过程

这个项目的推进顺序不是「先排需求再开发」，而是「**先补一块知识，再把它落成一块代码**」。所以：

- README 里的完成状态 = 我的学习进度，不是产品交付进度。
- 没想清楚的东西不会假装已经做完，状态标记只用三种：`✅ 已落地` ｜ `🚧 部分完成` ｜ `📋 规划中`。
- 允许推倒重来：某个模块学明白之后发现自己写的那版架构不对，就重写，并记录下为什么改。

### 学习记录：[log.md](file:///d:/code/agent-workbench/log.md)

`log.md` 是本项目的**第一手学习笔记**，按日期追加，不追求成文，追求「三个月后的自己还能看懂当时卡在哪」。每次动手后固定记四件事：

```markdown
## 2026/10/27 手写 ReAct 循环

- 想搞清楚：不借助框架，Agent 的「思考-行动-观察」循环长什么样
- 动手做了：工具注册表 + System Prompt 输出契约 + max_steps 熔断
- 卡在哪：模型偶尔不按「行动/参数」格式输出，靠异常捕获回灌重试兜住
- 结论：文本解析很脆，下一步该上 Function Calling
- 待验证：工具数量涨到 10 个以上时，Prompt 里的工具清单还能不能撑住
```

其中「卡在哪」「待验证」两栏是重点——它们直接决定下一阶段做什么，也是复盘时最有价值的部分。

## 🔁 已经跑通的最小闭环

```text
        ┌──────────────────────────────────────────────┐
        │  System Prompt（工具清单 + 输出格式契约）      │
        └───────────────────────┬──────────────────────┘
                                ▼
  用户输入 ──► messages ──► call_llm ──► 模型输出文本
                                ▲              │
                                │              ▼
                                │       解析「思考/行动/参数」
                                │              │
                     Observation 回填          ├─ 有行动 ──► TOOLS[action](**params)
                                │              │                │
                                └──────────────┤                │
                                               ├─ 有最终答案 ──► 返回并结束
                                               │
                                               └─ 格式错误 ──► 错误信息回灌重试
                                               │
                                        step >= max_steps ──► 熔断终止
```

| 模块 | 涉及技术点 | 实现位置 | 状态 |
| --- | --- | --- | --- |
| ReAct 主循环 | Thought → Action → Observation 循环、`最终答案` 终止判定 | `run_agent` | ✅ 已落地 |
| 工具注册表 | Registry 模式统一登记工具名/描述/执行函数，新增工具不改主循环 | `TOOLS` | ✅ 已落地 |
| Prompt 契约 | System Prompt 注入工具清单、约束输出格式、解析失败回灌重试 | `build_system_prompt` | ✅ 已落地 |
| 熔断保护 | `max_steps` 上限，防止 Doom-loop 无限调用 | `run_agent` | ✅ 已落地 |
| 模型接入 | DashScope OpenAI 兼容协议、`urllib` 直连、低温度稳定输出 | `call_llm` | 🚧 单厂商硬编码，模型名写死 `qwen-plus` |
| 工具集 | 天气 / 时间查询工具 | `get_weather` | 🚧 仅模拟天气（硬编码返回），时间工具未做 |
| 记忆管理 | 对话上下文累积 | `messages` | 🚧 无截断/压缩，长对话会溢出 |

## 🗺️ 迭代路线图

每个阶段都对应一批要补的知识点。**阶段内的功能不是目的，把知识点落地成代码才是。**

### Phase 2：模型网关与记忆（学会「调用层」怎么抽象）

> 学习目标：理解为什么需要网关、流式响应、重试退避；理解上下文窗口是稀缺资源。

| 模块 | 涉及技术点 | 状态 |
| --- | --- | --- |
| LLM Gateway | 统一调用层，适配 智谱 / 百炼 / DeepSeek / Ollama，按 `MODEL_PROVIDER` 路由 | 📋 规划中（`.env` 已预留字段） |
| 容错 | 超时、限流、失败重试与指数退避 | 📋 规划中 |
| 流式输出 | SSE Chunk 增量解析与终端增量渲染 | 📋 规划中 |
| Function Calling | 用原生 `tools` schema 替代文本正则解析，消除格式歧义 | 📋 规划中 |
| 上下文管理 | Token 计数、滑动窗口截断、历史摘要压缩 | 📋 规划中 |
| 真实工具 | 本地文件读写、Shell 执行（超时 + 白名单） | 📋 规划中 |

### Phase 3：RAG 与个人知识库（学会「私有数据怎么进模型」）

> 学习目标：搞清分块策略、Embedding、召回与重排各自的失效边界；理解幻觉是可以被检索约束住的。

| 模块 | 涉及技术点 | 状态 |
| --- | --- | --- |
| 文档流水线 | Markdown / PDF 解析 → 分块（Chunking）→ Embedding | 📋 规划中 |
| 向量检索 | ChromaDB / Qdrant 持久化、增量索引更新 | 📋 规划中 |
| 检索质量 | top-k 召回、Rerank 重排、上下文组装 | 📋 规划中 |
| 幻觉治理 | Prompt 约束回答必须附带引用来源 | 📋 规划中 |
| WIKI 助手 | 个人笔记增量问答，落到「知识问答」场景 | 📋 规划中 |

### Phase 4：工程化重构与可观测性（学会「怎么知道它好不好」）

> 学习目标：用框架重写一遍手写循环并说出取舍；建立「没有评测就没有优化」的判断。

| 模块 | 涉及技术点 | 状态 |
| --- | --- | --- |
| 状态机重构 | 引入 LangGraph StateGraph 承载循环状态，对比手写版架构优劣 | 📋 规划中 |
| 可观测性 | 结构化日志（Loguru）、调用链路追踪、Token/耗时统计 | 📋 规划中 |
| 评测体系 | 测试集构建、工具调用准确率、RAG 召回率 | 📋 规划中 |
| 交付 | Pydantic 配置校验、Docker 封装、环境变量分层管理 | 📋 规划中 |

### Phase 5：多智能体协作（学会「怎么让多个 Agent 分工」）

> 学习目标：搞清角色分工的收益边界——什么时候多智能体是加分，什么时候只是徒增延迟和成本。

## 🛠️ 技术栈

**当前依赖**（`hello-agent.py`）：`json` / `os` / `urllib.request` / `pathlib`，纯标准库，无第三方包。

**后续规划**：

- **语言**：Python 3.10+（开发环境 3.11.2）
- **模型交互**：`httpx`（异步请求）、DashScope / OpenAI SDK
- **服务与终端**：`FastAPI`、`Typer`、`Rich`
- **数据与向量**：`Pydantic`（校验）、`ChromaDB` / `Qdrant`
- **工程化**：`Loguru`（日志）、Docker

## ⚙️ 本地运行备忘（写给自己）

当前阶段不为他人上手体验做优化，这里只留一份最小备忘，避免隔几天回来忘了怎么跑。

1. 复制配置模板并填入 Key（`.env` 已 gitignore，仓库只保留 [sample.env](file:///d:/code/agent-workbench/sample.env) 模板）：

```bash
cp sample.env .env
# Windows PowerShell: Copy-Item sample.env .env
```

`sample.env` 里两个字段：`MODEL_PROVIDER`（多供应商路由预留，当前仅实现 dashscope 直连）、`API_KEY`（换成自己的 Key，不要提交真实 Key）。

2. 运行：

```bash
python hello-agent.py
```

3. 输入问题后，终端会依次打印 `模型输入 → 模型输出 → 工具调用 → 观察结果`，最后输出 `✅ Agent 最终回答`。

> 注意：`get_weather` 是硬编码的模拟工具，只用于验证调用链路，不请求真实天气接口。
